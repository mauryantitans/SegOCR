## Introduction

A library catalogue starts as a spreadsheet: one row per book, and a column **Authors** containing `Abraham Silberschatz, Henry F. Korth, S. Sudarshan`. A second column **Tags** holds `databases,textbook,sql`. When the spreadsheet becomes a MySQL table, those columns are usually imported as `VARCHAR` — and the database inherits a design that cannot answer simple questions reliably:

- *Which books did Henry F. Korth write?* — a substring search that also matches "Korthals".
- *Which books are tagged `sql`?* — `LIKE '%sql%'` also matches `mysql` and `nosql`.
- *How many authors does each book have?* — string arithmetic on commas.
- *Rename an author everywhere* — `REPLACE()` over every string that might contain the name.
- *Guarantee that every author exists in the authors table* — impossible; a foreign key cannot point *into* a string.

**First normal form (1NF)** is the rule that removes this whole class of problems: every attribute value in every row is a **single, atomic value** — no lists, no sets, no repeating groups of columns. In relational terms it is what makes a table a *relation* at all, and it is the precondition for the higher normal forms in this module.

This lesson demonstrates each 1NF violation for real in MySQL — comma-separated lists, `author1/author2/author3` columns, and JSON arrays — then converts them into proper **junction tables** using `JSON_TABLE` and `INSERT … SELECT DISTINCT`, and proves the conversion lossless. It ends with the pragmatic question every MySQL engineer faces since JSON columns arrived: *is a JSON array a 1NF violation, and when is it acceptable?*

:::note[Dataset]
The examples use the **library** dataset (12 books, 16 authors, a `book_authors` junction table). We build an unnormalized catalogue `catalog_flat` from it, so you can compare our converted tables with the dataset's own normalized design.
:::

## DBMS Theory

:::theory[First normal form]
**Codd's definition (1970–1972):** a relation is in first normal form if every attribute is defined on a domain of **simple** (atomic) values — no attribute value is itself a set, list or relation. A relation is a *set of tuples*, and each tuple has exactly one value for each attribute.

**Elmasri & Navathe:** 1NF "states that the domain of an attribute must include only atomic (simple, indivisible) values and that the value of any attribute in a tuple must be a single value from the domain of that attribute." It disallows **multivalued attributes**, **composite attributes** used as one value, and **nested relations** (relations within relations).
:::

Three kinds of violation appear in practice:

| Violation | Example | Why it breaks the model |
|---|---|---|
| **Multivalued attribute** (list in a cell) | `authors = 'Elmasri, Navathe'` | One cell holds several facts; the DBMS sees one opaque string |
| **Repeating group across columns** | `author1, author2, author3` | A fixed upper bound baked into the schema; "the same attribute" lives in several columns |
| **Nested relation / document** | `authors = [{"name":…, "order":1}, …]` | A relation stored inside an attribute |

Repeating-group columns technically hold one value per cell, so some authors classify them as "1NF but bad design". The mainstream textbook view (and the one this course follows) treats them as a **repeating group** that 1NF normalization removes, because the columns hold the same kind of fact and the schema has to change when a book gains a fourth author.

**Atomicity is relative to use.** C. J. Date (*SQL and Relational Theory*) points out that no value is atomic in an absolute sense: a date has year, month and day; a string has characters. What 1NF really requires is that the DBMS never has to look *inside* a value to answer the questions the application asks. A phone number is atomic if you only store and display it; it is not atomic if you routinely query by area code. The practical test: **if you need to search, join, count, constrain or update individual parts of a value, those parts should be separate values.**

**Normalizing to 1NF.** The standard transformation for a multivalued attribute A of relation R(K, …, A) is to remove A and create a new relation R_A(K, A) whose key is **(K, A)** — one row per element. If element order matters (author order on a title page), add an ordinal attribute. If the elements are entities with their own facts (authors with birth years), the new relation becomes a **junction table** between two entity tables.

## Why It Exists

The relational model's power comes from operating on **sets of values with one algebra**: selection, projection, join, aggregation. Every operator assumes that the values it compares are atomic. A list inside a cell is invisible to all of them:

- **Selection** (`WHERE`) needs exact predicates on elements; with a list you fall back to substring matching, which is both slow and wrong.
- **Join** (`ON a.author_id = b.author_id`) needs one value per row; a list cannot be joined without first being parsed.
- **Aggregation** (`COUNT`, `GROUP BY author`) needs one row per element.
- **Integrity constraints** — primary keys, foreign keys, `UNIQUE`, `CHECK` — apply to whole column values. A foreign key cannot say "every name in this list exists in `authors`", and `UNIQUE` cannot stop a list from containing the same tag twice.
- **Indexes** in a B+ tree order whole values. An index on `'Baron Schwartz, Peter Zaitsev, Vadim Tkachenko'` can find books whose author list *starts with* Baron Schwartz, but not books by Peter Zaitsev.

Without 1NF, each of those capabilities has to be re-implemented, badly, in string functions or application code. Bill Karwin's *SQL Antipatterns* calls the comma-separated list **"Jaywalking"** — crossing the street outside the crosswalk to save a few steps (an intersection table) — and it is one of the most common design mistakes in production schemas.

## Internal Working

:::internals[What InnoDB sees in a list column]
To InnoDB, `'databases,textbook,sql'` is a sequence of bytes in a `VARCHAR` field, compared using the column's collation. Consequences:

- **A secondary index on the column** sorts entire strings. It supports `= 'databases,textbook,sql'` and prefix patterns `LIKE 'databases%'`, but a search for one *element* in the middle (`LIKE '%sql%'`, `FIND_IN_SET('sql', tags)`) cannot use the B+ tree for seeking: every row (or every index entry) must be read and the predicate evaluated.
- **Updating one element rewrites the whole value** — the row is modified, undo and redo records are written, and every index on the column is updated, even if only one tag changed.
- **The junction table** stores one `(book_id, tag)` row per element in its own clustered index. Finding books for a tag is then a B+ tree seek on a secondary index `(tag)` or on a primary key `(tag, book_id)`; adding a tag is one row insert.
:::

MySQL 8.0.17 added a feature that blurs this boundary: the **multi-valued index**. Defined on a JSON array with `CAST(col->'$' AS CHAR(n) ARRAY)`, it stores **one index entry per array element**, so `'sql' MEMBER OF (tags)` and `JSON_CONTAINS` / `JSON_OVERLAPS` can seek instead of scan. Internally it is still a B+ tree whose entries point back to the row — essentially the index of a junction table, maintained automatically. It solves the *search* problem of embedded lists but none of the *integrity* problems: there is still no foreign key from an array element, and no uniqueness across rows.

## MySQL Implementation

Build the unnormalized catalogue the way an import from a spreadsheet would produce it: authors and tags as comma-separated strings.

```sql run
CREATE TABLE catalog_flat (
  book_id INT UNSIGNED PRIMARY KEY,
  title   VARCHAR(200) NOT NULL,
  authors VARCHAR(500) NOT NULL,
  tags    VARCHAR(200) NOT NULL
);
INSERT INTO catalog_flat (book_id, title, authors, tags)
SELECT b.book_id, b.title,
       GROUP_CONCAT(a.name ORDER BY ba.author_order SEPARATOR ', '),
       ELT(b.book_id, 'databases,storage-engines,internals', 'distributed-systems,databases,architecture',
           'mysql,performance,databases', 'sql,anti-patterns,databases', 'databases,textbook,sql',
           'databases,textbook', 'sql,relational-theory', 'science-fiction,classic', 'literary-fiction',
           'literary-fiction,magical-realism', 'science-fiction', 'magical-realism')
FROM books b
JOIN book_authors ba ON ba.book_id = b.book_id
JOIN authors a       ON a.author_id = ba.author_id
GROUP BY b.book_id, b.title;
SELECT book_id, title, authors, tags FROM catalog_flat ORDER BY book_id LIMIT 7;
```

Now ask the catalogue a simple question: *which books are tagged `sql`?*

```sql run
-- Substring search: wrong answer
SELECT book_id, title, tags FROM catalog_flat WHERE tags LIKE '%sql%' ORDER BY book_id;
```

Book 3 is tagged `mysql`, not `sql`, yet it matches. `FIND_IN_SET` compares whole list elements and gets the right answer — as long as the separator is exactly a comma with no spaces:

```sql run
SELECT book_id, title, tags FROM catalog_flat WHERE FIND_IN_SET('sql', tags) > 0 ORDER BY book_id;
```

```sql run
-- The authors list uses ', ' (comma + space): FIND_IN_SET silently misses everyone but the first author
SELECT book_id, title FROM catalog_flat WHERE FIND_IN_SET('Henry F. Korth', authors) > 0;
```

The empty result is the worst kind of bug: no error, just a wrong answer. The list elements are `'Abraham Silberschatz'`, `' Henry F. Korth'` (with a leading space) and `' S. Sudarshan'`. Every query against a list column depends on formatting conventions the database cannot enforce.

## Syntax Breakdown

| Construct | What it does | 1NF relevance |
|---|---|---|
| `GROUP_CONCAT(x ORDER BY … SEPARATOR ', ')` | Aggregates rows into one delimited string | The *reverse* of normalization — fine for display, never for storage |
| `FIND_IN_SET(str, list)` | Position of `str` in a comma-separated list (0 if absent) | Exact element match; requires `,` without spaces; cannot use an index |
| `LIKE '%x%'` | Substring match | Matches inside other elements — false positives |
| `SUBSTRING_INDEX(s, delim, n)` | Text before the n-th delimiter (after it if n < 0) | Building block for splitting lists with a recursive CTE |
| `JSON_TABLE(doc, '$[*]' COLUMNS (…))` | Turns a JSON array into rows (a table function) | The idiomatic way to unnest arrays in MySQL 8.0+ |
| `col FOR ORDINALITY` | Row number inside `JSON_TABLE` (1, 2, 3 …) | Preserves element order (e.g. author order) |
| `JSON_ARRAYAGG(x)` | Aggregates rows into a JSON array | Builds a JSON document from normalized rows |
| `value MEMBER OF (json_array)` | True if the array contains the value (8.0.17+) | Can use a multi-valued index |
| `CAST(… AS CHAR(n) ARRAY)` in an index | Defines a multi-valued index (8.0.17+) | One index entry per array element |
| `SET('a','b',…)` column type | MySQL-specific set of up to 64 predefined members | Another multivalued attribute; members are fixed in the DDL |

:::standard[Standard SQL vs MySQL]
Standard SQL has had collection types (`ARRAY`, `MULTISET`) since SQL:1999/2003 and `JSON_TABLE` since SQL:2016. MySQL implements `JSON_TABLE` but has **no SQL array type**; its `SET` type and `FIND_IN_SET` are MySQL-specific. PostgreSQL offers native arrays with `unnest()` and GIN indexes, which is why "arrays in columns" is a more common debate in PostgreSQL shops.
:::

## Practical Examples

### 1. Repeating groups across columns

The other classic shape spreads the list over fixed columns. Every query must repeat itself per column, and the fourth author has nowhere to go:

```sql run
CREATE TABLE catalog_cols (
  book_id INT UNSIGNED PRIMARY KEY,
  title   VARCHAR(200) NOT NULL,
  author1 VARCHAR(100) NOT NULL,
  author2 VARCHAR(100) NULL,
  author3 VARCHAR(100) NULL
);
INSERT INTO catalog_cols
SELECT book_id, title,
       SUBSTRING_INDEX(authors, ', ', 1),
       NULLIF(SUBSTRING_INDEX(SUBSTRING_INDEX(authors, ', ', 2), ', ', -1), SUBSTRING_INDEX(authors, ', ', 1)),
       NULLIF(SUBSTRING_INDEX(SUBSTRING_INDEX(authors, ', ', 3), ', ', -1), SUBSTRING_INDEX(SUBSTRING_INDEX(authors, ', ', 2), ', ', -1))
FROM catalog_flat;
-- "Books by Peter Zaitsev" must check every column
SELECT book_id, title FROM catalog_cols
WHERE 'Peter Zaitsev' IN (author1, author2, author3);
```

Counting authors per book becomes `(author1 IS NOT NULL) + (author2 IS NOT NULL) + …`, and "all authors with their books" needs a `UNION ALL` of three `SELECT`s. A fourth co-author requires `ALTER TABLE` — the schema encodes a data value (the maximum number of authors).

### 2. Converting the list to 1NF with JSON_TABLE

`JSON_TABLE` unnests a JSON array into rows. A comma-separated string becomes a JSON array by quoting the elements — safe here because no author name contains a double quote (for arbitrary text use the recursive-CTE splitter in *Alternative Approaches*):

```sql run
SELECT f.book_id, j.author_order, j.author_name
FROM catalog_flat AS f,
     JSON_TABLE(CONCAT('["', REPLACE(f.authors, ', ', '","'), '"]'),
                '$[*]' COLUMNS (author_order FOR ORDINALITY,
                                author_name  VARCHAR(100) PATH '$')) AS j
WHERE f.book_id IN (3, 5, 6)
ORDER BY f.book_id, j.author_order;
```

`FOR ORDINALITY` numbers the elements, preserving the title-page order. Now create the 1NF target schema — an entity table for authors and a junction table — and migrate:

```sql run
CREATE TABLE lib_author (
  author_id   INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  author_name VARCHAR(100) NOT NULL,
  CONSTRAINT uq_lib_author_name UNIQUE (author_name)
);
CREATE TABLE lib_book_author (
  book_id      INT UNSIGNED NOT NULL,
  author_id    INT UNSIGNED NOT NULL,
  author_order TINYINT UNSIGNED NOT NULL,
  PRIMARY KEY (book_id, author_id),
  CONSTRAINT uq_lib_book_author_order UNIQUE (book_id, author_order),
  CONSTRAINT fk_lba_book   FOREIGN KEY (book_id)   REFERENCES catalog_flat (book_id),
  CONSTRAINT fk_lba_author FOREIGN KEY (author_id) REFERENCES lib_author (author_id)
);
INSERT INTO lib_author (author_name)
SELECT DISTINCT j.author_name
FROM catalog_flat AS f,
     JSON_TABLE(CONCAT('["', REPLACE(f.authors, ', ', '","'), '"]'),
                '$[*]' COLUMNS (author_name VARCHAR(100) PATH '$')) AS j
ORDER BY j.author_name;
INSERT INTO lib_book_author (book_id, author_id, author_order)
SELECT f.book_id, a.author_id, j.author_order
FROM catalog_flat AS f,
     JSON_TABLE(CONCAT('["', REPLACE(f.authors, ', ', '","'), '"]'),
                '$[*]' COLUMNS (author_order FOR ORDINALITY,
                                author_name  VARCHAR(100) PATH '$')) AS j
JOIN lib_author AS a ON a.author_name = j.author_name;
SELECT (SELECT COUNT(*) FROM lib_author)      AS authors,
       (SELECT COUNT(*) FROM lib_book_author) AS book_author_links;
```

The migration produced 15 authors and 17 authorship links. `SELECT DISTINCT` stores each author once even though Ursula K. Le Guin and Haruki Murakami each appear on two books. (The dataset's `authors` table has 16 rows: the list design could never represent the author who has no book in the catalogue — the insertion anomaly from the first lesson, in another shape.) The constraints now express rules the string never could: an author appears at most once per book (primary key), each position on the title page is used once (`uq_lib_book_author_order`), and every link points at an existing book and author (foreign keys).

### 3. The questions, answered correctly

```sql run
SELECT a.author_name, COUNT(*) AS books
FROM lib_author a JOIN lib_book_author ba ON ba.author_id = a.author_id
GROUP BY a.author_id, a.author_name
HAVING COUNT(*) > 1
ORDER BY a.author_name;
```

```sql run
-- Books by Henry F. Korth: an exact, indexable equality instead of string parsing
SELECT f.book_id, f.title
FROM lib_author a
JOIN lib_book_author ba ON ba.author_id = a.author_id
JOIN catalog_flat f     ON f.book_id = ba.book_id
WHERE a.author_name = 'Henry F. Korth';
```

Renaming an author is now a one-row update in `lib_author`, and it is impossible to misspell an author on one book only.

### 4. A JSON array column — and a multi-valued index

Since MySQL 5.7 a column can be `JSON`. Store the tags as a JSON array and add a **multi-valued index**:

```sql run
CREATE TABLE catalog_json (
  book_id INT UNSIGNED PRIMARY KEY,
  title   VARCHAR(200) NOT NULL,
  tags    JSON NOT NULL,
  INDEX idx_catalog_json_tags ((CAST(tags AS CHAR(40) ARRAY)))
);
INSERT INTO catalog_json
SELECT book_id, title, CAST(CONCAT('["', REPLACE(tags, ',', '","'), '"]') AS JSON)
FROM catalog_flat;
ANALYZE TABLE catalog_json;
SELECT book_id, title, tags FROM catalog_json WHERE 'sql' MEMBER OF (tags) ORDER BY book_id;
```

`MEMBER OF` matches whole elements, so `mysql` no longer creeps in. The plan shows that the multi-valued index is used to find the matching rows:

```sql run
EXPLAIN SELECT book_id, title FROM catalog_json WHERE 'sql' MEMBER OF (tags);
```

`JSON_TABLE` turns the array back into rows whenever relational processing is needed — for example a tag histogram:

```sql run
SELECT jt.tag, COUNT(*) AS books
FROM catalog_json AS c,
     JSON_TABLE(c.tags, '$[*]' COLUMNS (tag VARCHAR(40) PATH '$')) AS jt
GROUP BY jt.tag
ORDER BY books DESC, jt.tag
LIMIT 5;
```

But integrity is still the application's problem. Nothing stops a duplicate or misspelled tag inside the array:

```sql run
UPDATE catalog_json SET tags = JSON_ARRAY_APPEND(tags, '$', 'Databases ') WHERE book_id = 6;
SELECT book_id, tags FROM catalog_json WHERE book_id = 6;
```

In a junction table `book_tag(book_id, tag)` with a foreign key to a `tag` table, `'Databases '` would have been rejected (or at least caught by `UNIQUE` after normalizing case and whitespace).

## Execution Walkthrough

Trace the conversion of one book's author list into 1NF rows, and then prove that the whole conversion is lossless by rebuilding the original strings from the normalized tables.

```walkthrough
title: From one VARCHAR list to junction rows, and back
steps:
  - title: "1. The unnormalized value"
    explain: Book 5 stores three facts (three authorships) in one cell. To the DBMS it is a single 50-character string.
    sql: |
      SELECT book_id, authors, CHAR_LENGTH(authors) AS chars FROM catalog_flat WHERE book_id = 5;
  - title: "2. Turn the list into a JSON array"
    explain: Replacing the separator with '","' and wrapping in [" … "] produces a valid JSON array literal. JSON_VALID confirms it parses.
    sql: |
      SELECT CONCAT('["', REPLACE(authors, ', ', '","'), '"]') AS as_json,
             JSON_VALID(CONCAT('["', REPLACE(authors, ', ', '","'), '"]')) AS is_valid
      FROM catalog_flat WHERE book_id = 5;
  - title: "3. JSON_TABLE emits one row per element"
    explain: The table function is evaluated once per catalog_flat row (it is laterally correlated with f). FOR ORDINALITY supplies the element's position.
    sql: |
      SELECT j.author_order, j.author_name
      FROM catalog_flat f,
           JSON_TABLE(CONCAT('["', REPLACE(f.authors, ', ', '","'), '"]'),
                      '$[*]' COLUMNS (author_order FOR ORDINALITY, author_name VARCHAR(100) PATH '$')) j
      WHERE f.book_id = 5 ORDER BY j.author_order;
  - title: "4. The stored 1NF rows"
    explain: Each authorship is now one row of lib_book_author, joined to its author entity. Every value is atomic.
    sql: |
      SELECT ba.book_id, ba.author_order, a.author_id, a.author_name
      FROM lib_book_author ba JOIN lib_author a ON a.author_id = ba.author_id
      WHERE ba.book_id = 5 ORDER BY ba.author_order;
  - title: "5. Rebuild every list and compare with EXCEPT"
    explain: GROUP_CONCAT in author_order reconstructs the original strings. Both EXCEPT directions return zero rows, so the conversion lost nothing and invented nothing.
    sql: |
      WITH rebuilt AS (
        SELECT ba.book_id, GROUP_CONCAT(a.author_name ORDER BY ba.author_order SEPARATOR ', ') AS authors
        FROM lib_book_author ba JOIN lib_author a ON a.author_id = ba.author_id
        GROUP BY ba.book_id)
      SELECT (SELECT COUNT(*) FROM (SELECT book_id, authors FROM catalog_flat EXCEPT SELECT book_id, authors FROM rebuilt) d1) AS lost,
             (SELECT COUNT(*) FROM (SELECT book_id, authors FROM rebuilt EXCEPT SELECT book_id, authors FROM catalog_flat) d2) AS invented;
  - title: "6. Compare with the dataset's own design"
    explain: The library dataset was designed in 1NF from the start (authors + book_authors). Our migrated links match it exactly once author names are mapped to the dataset's author ids.
    sql: |
      SELECT COUNT(*) AS mismatched_links
      FROM (SELECT ba.book_id, a.author_id, ba.author_order
            FROM lib_book_author lba
            JOIN lib_author la ON la.author_id = lba.author_id
            JOIN authors a     ON a.name = la.author_name
            JOIN book_authors ba ON ba.book_id = lba.book_id AND ba.author_id = a.author_id AND ba.author_order = lba.author_order
            ) AS matched
      RIGHT JOIN book_authors x ON x.book_id = matched.book_id AND x.author_id = matched.author_id
      WHERE matched.book_id IS NULL;
```

## Output

After normalization the catalogue's facts live in three tables: `catalog_flat` (books — we keep its `authors` and `tags` columns only for comparison; in a real migration they would be dropped), `lib_author` (one row per author) and `lib_book_author` (one row per authorship). The summary below shows the shape change:

```sql run
SELECT 'catalog_flat.authors (lists)' AS representation, COUNT(*) AS rows_stored,
       SUM(CHAR_LENGTH(authors) - CHAR_LENGTH(REPLACE(authors, ',', '')) + 1) AS authorships
FROM catalog_flat
UNION ALL
SELECT 'lib_book_author (1NF)', COUNT(*), COUNT(*) FROM lib_book_author;
```

Twelve list values hold the same 17 authorships that the junction table stores as 17 rows. The difference is not storage size — it is that each authorship is now an addressable fact that the DBMS can index, join, count, constrain and update individually. Counting authorships in the list representation required string arithmetic (`length − length without commas + 1`), which silently breaks the first time a name contains a comma ("Martin Luther King, Jr.").

## Alternative Approaches

**Splitting without JSON: a recursive CTE.** Works for any text, including values with quotes, using `SUBSTRING_INDEX` to peel off one element per iteration:

```sql run
WITH RECURSIVE split AS (
  SELECT book_id, 1 AS pos,
         SUBSTRING_INDEX(tags, ',', 1) AS tag,
         IF(LOCATE(',', tags) > 0, SUBSTRING(tags, LOCATE(',', tags) + 1), NULL) AS rest
  FROM catalog_flat
  UNION ALL
  SELECT book_id, pos + 1,
         SUBSTRING_INDEX(rest, ',', 1),
         IF(LOCATE(',', rest) > 0, SUBSTRING(rest, LOCATE(',', rest) + 1), NULL)
  FROM split
  WHERE rest IS NOT NULL
)
SELECT book_id, pos, tag FROM split WHERE book_id IN (3, 4) ORDER BY book_id, pos;
```

**Choosing a representation for multivalued data:**

| Representation | Search one element | Integrity (FK, UNIQUE) | Order | Schema change for more elements | Best for |
|---|---|---|---|---|---|
| Junction table (1NF) | B+ tree seek | Full | Ordinal column | None | System-of-record data, anything you join or constrain |
| Comma-separated `VARCHAR` | Scan with `FIND_IN_SET` | None | Implicit, fragile | None | Never for stored data; display output only |
| `author1 … authorN` columns | `IN (col1, …)`, one index per column | Per column only | Column position | `ALTER TABLE` | Rare fixed-arity cases (e.g. `address_line1/2`) |
| `JSON` array + multi-valued index | Index seek with `MEMBER OF`, `JSON_CONTAINS`, `JSON_OVERLAPS` | None across rows | Array order | None | Read-mostly attributes, tags you never join, payloads from APIs |
| `SET` type | `FIND_IN_SET` / bit tests, scan | Members fixed in DDL | None | `ALTER TABLE` to add members | Small fixed flag sets (≤ 64) |

**Is a JSON column a 1NF violation?** Strictly, yes: an array is a non-atomic value, and Codd's 1NF forbids it. Date argues that a relation-valued attribute can be legitimate if the DBMS provides operators over it — and MySQL does (`JSON_TABLE`, `MEMBER OF`, multi-valued indexes). The pragmatic rule used by experienced MySQL engineers: **a JSON array is acceptable when the elements are not entities with their own facts, are never the target of a foreign key, and are read and written as a unit.** Labels on a support ticket can qualify; authors of a book do not (they have birth years, other books, and must be renamed consistently).

## Performance Analysis

On 12 rows nothing is slow; what matters is how each design scales, which the plans reveal.

```sql run
CREATE INDEX idx_catalog_flat_tags ON catalog_flat (tags);
ANALYZE TABLE catalog_flat;
EXPLAIN SELECT book_id FROM catalog_flat WHERE FIND_IN_SET('sql', tags) > 0;
```

Even with an index on `tags`, `FIND_IN_SET` cannot seek: the plan shows `type: index` — a full scan of all 12 index entries (*Using index* only means the table rows themselves are not read) with the function evaluated on each one. Compare with a junction table and an index on the element:

```sql run
CREATE TABLE lib_book_tag (
  book_id INT UNSIGNED NOT NULL,
  tag     VARCHAR(40)  NOT NULL,
  PRIMARY KEY (book_id, tag),
  INDEX idx_lib_book_tag_tag (tag, book_id)
);
INSERT INTO lib_book_tag (book_id, tag)
SELECT f.book_id, jt.tag
FROM catalog_flat f,
     JSON_TABLE(CONCAT('["', REPLACE(f.tags, ',', '","'), '"]'), '$[*]' COLUMNS (tag VARCHAR(40) PATH '$')) jt;
ANALYZE TABLE lib_book_tag;
EXPLAIN SELECT book_id FROM lib_book_tag WHERE tag = 'sql';
```

The junction-table plan is a `ref` lookup on `idx_lib_book_tag_tag` — a B+ tree descent to the first `'sql'` entry followed by a short range read, independent of how many books exist. `ANALYZE TABLE` was run because these tables were just created; without statistics the optimizer's row estimates would be guesses.

| Operation | CSV column | Junction table | JSON + multi-valued index |
|---|---|---|---|
| Find rows with element x | O(n) scan | O(log n + matches) | O(log n + matches) |
| Add one element | Rewrite the string (whole row) | Insert one row | Rewrite the JSON value; index entries diffed |
| Remove an element everywhere | `REPLACE` over all rows, error-prone | `DELETE … WHERE tag = x` | `JSON_REMOVE` with `JSON_SEARCH` per row |
| Count per element | Split every row | `GROUP BY tag` on the index | `JSON_TABLE` unnest, then group |
| Storage overhead | Smallest | Key repeated per row + indexes | JSON binary format + index |

:::performance[Theory vs measurement]
These are access-path properties, not measured timings. With thousands of rows the scan-vs-seek difference becomes orders of magnitude; measure on your own data with `EXPLAIN ANALYZE` ([EXPLAIN ANALYZE](/lessons/m07-explain-analyze)).
:::

## Best Practices

:::best-practice[1NF in MySQL schemas]
1. **Never store delimited lists in a column of record.** Use a junction table with a composite primary key; add an ordinal column when order matters.
2. **Model list elements that are entities as entities.** Authors, tags with descriptions, roles with permissions — each gets its own table, and the list becomes a many-to-many relationship ([Relationship Patterns](/lessons/m05-relationship-patterns)).
3. **Use `GROUP_CONCAT` / `JSON_ARRAYAGG` for output, not storage.** Producing a list for display is fine; storing it is not.
4. **If you choose a JSON array, decide it deliberately:** elements are values (not entities), never referenced by FKs, read and written as a unit; add a multi-valued index if you search by element; validate shape with a `CHECK (JSON_SCHEMA_VALID(…))` constraint (8.0.17+).
5. **Migrate legacy lists with set-based SQL** (`JSON_TABLE` or a recursive CTE) into new tables, verify with an `EXCEPT` round trip, then drop the list column.
6. **Treat `author1/author2/author3` columns as a list** and normalize them the same way, unless the positions have genuinely different meanings (billing vs shipping address).
:::

## Common Mistakes

**Mistake 1 — `LIKE '%x%'` on a list.** Shown above: `'%sql%'` matched `mysql`. Wrapping with delimiters (`CONCAT(',', tags, ',') LIKE '%,sql,%'`) fixes the false positive but still scans every row and still depends on formatting.

**Mistake 2 — a foreign key "into" a list.** It is impossible, and MySQL says so when you try to reference a list column from a junction-like design:

```sql run error
CREATE TABLE author_bio (
  author_name VARCHAR(500) NOT NULL,
  bio TEXT,
  CONSTRAINT fk_bio_author FOREIGN KEY (author_name) REFERENCES catalog_flat (authors)
);
```

A foreign key needs an index whose leading columns are the referenced column(s), and even with one it would match whole strings, never individual names.

**Mistake 3 — trusting `FIND_IN_SET` with `', '` separators.** It returned no rows for Henry F. Korth because the stored element was `' Henry F. Korth'`. If you must query legacy lists, normalize separators first — better, migrate.

**Mistake 4 — splitting on a delimiter that occurs inside values.** "Martin Luther King, Jr." or "Smith, John" contain the separator. Real migrations must inspect the data (`WHERE authors LIKE '%,%,%'` for suspicious counts) before splitting.

**Mistake 5 — believing a multi-valued index makes JSON arrays "normalized".** It fixes search performance only. Example 4 showed a misspelled, duplicated tag `'Databases '` accepted without complaint.

## Industry Application

- **E-commerce catalogues** keep product ↔ category and product ↔ tag relationships in junction tables because merchandising teams query, rename and constrain them constantly; the storefront API then emits JSON arrays built with `JSON_ARRAYAGG` or in application code.
- **SaaS platforms** often store user-defined labels or feature flags as JSON arrays with multi-valued indexes — values without their own attributes, read with the parent row. When labels gain colours, owners and permissions, teams migrate them to tables.
- **Legacy and spreadsheet migrations** (CRM exports, survey tools) are full of "Jaywalking" columns. The migration scripts look exactly like this lesson: unnest with `JSON_TABLE` or a recursive CTE, `INSERT … SELECT DISTINCT` into entity tables, verify with `EXCEPT`.
- **Event and log ingestion** lands semi-structured JSON in MySQL or a warehouse first, then extracts the parts that are queried relationally into typed, 1NF tables — a pattern discussed in [JSON in MySQL](/lessons/m13-json).
- **Code review checklists** at many companies flag `VARCHAR` columns named `*_ids`, `*_list` or `tags` as a design smell requiring justification.

id: ex1
title: Exact tag search on a list column
difficulty: easy
setup: |
  CREATE TABLE posts (post_id INT PRIMARY KEY, title VARCHAR(100) NOT NULL, tags VARCHAR(200) NOT NULL);
  INSERT INTO posts VALUES
    (1, 'Indexing basics', 'mysql,indexes'),
    (2, 'Window functions', 'sql,analytics'),
    (3, 'Document stores', 'nosql,json'),
    (4, 'Writing joins', 'sql,joins'),
    (5, 'PostgreSQL arrays', 'postgresql,sql');

prompt: |
  The legacy table `posts(post_id, title, tags)` stores tags as a comma-separated list **without spaces**.
  Return `post_id` and `title` of every post tagged exactly `sql` (not `mysql`, `nosql` or `postgresql`),
  ordered by `post_id`.
hints:
  - "LIKE '%sql%' matches inside other tags."
  - "FIND_IN_SET('sql', tags) returns the 1-based position of an exact element, 0 if absent."
solution: |
  SELECT post_id, title FROM posts WHERE FIND_IN_SET('sql', tags) > 0 ORDER BY post_id;
orderMatters: true
explanation: |
  Posts 2, 4 and 5 are tagged `sql`. `LIKE '%sql%'` would also return posts 1 and 3. `FIND_IN_SET` compares

```exercise
id: ex2
title: Authors per book from the list
difficulty: medium
setup: |
  CREATE TABLE catalog_flat AS
  SELECT b.book_id, b.title, GROUP_CONCAT(a.name ORDER BY ba.author_order SEPARATOR ', ') AS authors
  FROM books b JOIN book_authors ba ON ba.book_id = b.book_id JOIN authors a ON a.author_id = ba.author_id
  GROUP BY b.book_id, b.title;
concepts: [json-table, first-normal-form]
prompt: |
  `catalog_flat(book_id, title, authors)` stores authors as a `', '`-separated list. Using `JSON_TABLE`,
  return `book_id` and `author_count` for books with **more than one** author, ordered by `book_id`.
hints:
  - "CONCAT('[\"', REPLACE(authors, ', ', '\",\"'), '\"]') turns the list into a JSON array."
  - "JSON_TABLE(…, '$[*]' COLUMNS (name VARCHAR(100) PATH '$')) gives one row per author; then GROUP BY book_id."
solution: |
  SELECT f.book_id, COUNT(*) AS author_count
  FROM catalog_flat f,
       JSON_TABLE(CONCAT('["', REPLACE(f.authors, ', ', '","'), '"]'),

  HAVING COUNT(*) > 1
  ORDER BY f.book_id;

id: ex3
title: Normalize a tag list into a junction table
difficulty: hard
kind: dml
setup: |
  CREATE TABLE posts (post_id INT PRIMARY KEY, title VARCHAR(100) NOT NULL, tags VARCHAR(200) NOT NULL);
  INSERT INTO posts VALUES
    (1, 'Indexing basics', 'mysql,indexes'),
    (2, 'Window functions', 'sql,analytics'),
    (3, 'Document stores', 'nosql,json'),
    (4, 'Writing joins', 'sql,joins,mysql');
concepts: [junction-table, first-normal-form, json-table]
prompt: |
  Bring `posts` into 1NF:

  1. Create `post_tag (post_id INT NOT NULL, tag VARCHAR(40) NOT NULL, PRIMARY KEY (post_id, tag))` with a
     foreign key `fk_post_tag_post` from `post_id` to `posts(post_id)`.
  2. Fill it from the `tags` lists (one row per post and tag).
  3. Drop the `tags` column from `posts`.

  The checker lists `post_tag` ordered by `post_id, tag`, plus the remaining columns of `posts`.
hints:
  - "JSON_TABLE(CONCAT('[\"', REPLACE(tags, ',', '\",\"'), '\"]'), '$[*]' COLUMNS (tag VARCHAR(40) PATH '$'))"
  - "Create the table with CONSTRAINT fk_post_tag_post FOREIGN KEY (post_id) REFERENCES posts (post_id), then INSERT … SELECT, then ALTER TABLE posts DROP COLUMN tags."
solution: |
  CREATE TABLE post_tag (
    post_id INT NOT NULL,
    tag     VARCHAR(40) NOT NULL,
    PRIMARY KEY (post_id, tag),
    CONSTRAINT fk_post_tag_post FOREIGN KEY (post_id) REFERENCES posts (post_id)
  );
  INSERT INTO post_tag (post_id, tag)
  SELECT p.post_id, j.tag
  FROM posts p,
       JSON_TABLE(CONCAT('["', REPLACE(p.tags, ',', '","'), '"]'), '$[*]' COLUMNS (tag VARCHAR(40) PATH '$')) AS j;
  ALTER TABLE posts DROP COLUMN tags;
check: |
  SELECT CAST(post_id AS CHAR) AS a, tag AS b FROM post_tag
  UNION ALL
  SELECT 'posts column', COLUMN_NAME FROM information_schema.COLUMNS
  WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'posts'
  UNION ALL
  SELECT 'fk', CONSTRAINT_NAME FROM information_schema.REFERENTIAL_CONSTRAINTS
  WHERE CONSTRAINT_SCHEMA = DATABASE() AND TABLE_NAME = 'post_tag'
  ORDER BY a, b;
explanation: |
  Nine `(post_id, tag)` rows replace four list values; `posts` keeps only `post_id` and `title`. The composite
  primary key prevents the same tag twice on one post — a rule the string could not enforce. A follow-up
  improvement is a `tag` entity table so tags can be renamed in one place and constrained by a foreign key.
```

```exercise
id: ex4
title: Tag histogram from a JSON column
difficulty: hard
setup: |
  CREATE TABLE tickets (ticket_id INT PRIMARY KEY, labels JSON NOT NULL);
  INSERT INTO tickets VALUES
    (1, '["billing", "urgent"]'), (2, '["login"]'), (3, '["billing"]'),
    (4, '["login", "urgent", "mobile"]'), (5, '[]');
concepts: [json-table, multi-valued-index]
prompt: |
  `tickets(ticket_id, labels JSON)` stores labels as JSON arrays. Return each `label` with the number of
  tickets carrying it (`tickets`), ordered by `tickets` descending, then `label` ascending.
hints:
  - "JSON_TABLE(t.labels, '$[*]' COLUMNS (label VARCHAR(40) PATH '$')) produces one row per array element."
  - "Ticket 5 has an empty array — JSON_TABLE produces no rows for it, which is what we want."
solution: |
  SELECT j.label, COUNT(*) AS tickets
  FROM tickets t,
       JSON_TABLE(t.labels, '$[*]' COLUMNS (label VARCHAR(40) PATH '$')) AS j
  GROUP BY j.label
  ORDER BY tickets DESC, j.label;
orderMatters: true
explanation: |
  `JSON_TABLE` is joined laterally to each ticket and unnests its array, giving relational rows that `GROUP BY`
  can count: billing 2, login 2, urgent 2, mobile 1. Because labels are plain values that are read with the
  ticket and never referenced elsewhere, a JSON array is a defensible design here — but counting still requires
  unnesting, which a `ticket_label` table would avoid.
```

```exercise
id: ex5
title: JSON array or junction table?
difficulty: challenge
kind: open
concepts: [first-normal-form, json-table, multi-valued-index, junction-table]
prompt: |
  A course-registration system stores `students(student_id, name, completed_courses JSON)`, e.g.
  `["CS-046", "CS-146"]`. Prerequisite checks run on every registration ("has the student completed every
  prerequisite of course X?"), the registrar sometimes renames course ids, and transcripts need grades per course.

  Argue whether `completed_courses` violates 1NF, list concrete problems with this design for each of the three
  requirements, and propose a schema. Say when, if ever, a JSON array would be acceptable in this system.
solution: |
  **1NF:** yes. The attribute holds a list of course ids; each element is a separate fact (student S completed
  course C). In Codd's sense the value is not atomic. MySQL's JSON functions let you query it, but that does not
  make the elements first-class values.

  **Problems:**
  - *Prerequisite checks:* need "all prerequisites ⊆ completed set" — doable with `JSON_CONTAINS(completed_courses,
    JSON_ARRAYAGG(prereq_id))`, but there is no foreign key from array elements to `courses`, so typos ("CS-46")
    silently make checks fail. A multi-valued index helps searching, not integrity.
  - *Renaming course ids:* requires `JSON_REPLACE`/`JSON_SEARCH` over every student row; easy to miss rows, and
    an `ON UPDATE CASCADE` foreign key is impossible.
  - *Grades:* a grade is a fact about the (student, course) pair. Putting it inside the array (objects with
    `{"course":…, "grade":…}`) nests a whole relation in one attribute — the "nested relation" violation.

  **Schema:** `completions(student_id FK → students, course_id FK → courses ON UPDATE CASCADE, term, grade,
  PRIMARY KEY (student_id, course_id, term))`. Prerequisite check becomes a relational-division / `NOT EXISTS`
  query on indexed keys; renames cascade; grades have a home.

  **When JSON is acceptable:** for data that is not referenced or constrained and is read as a unit — e.g. a
  student's UI preferences, or an immutable snapshot of an external API response kept for auditing — possibly
  with a `JSON_SCHEMA_VALID` check constraint.
```
